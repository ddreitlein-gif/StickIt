# StickIt v2 — Venue/Cloud Operations Notes

Operational recovery notes for David / system admins (not volunteer-facing;
volunteer material lives in `server/public/docs/venue/`).

## Rollback to v1.30.03 (Section 10)

- `main` is tagged `v1.30.03` (the pre-v2 commit). Render/Railway build from
  `server/` only: rollback = one-click redeploy of the previous deploy in the
  Render dashboard, or a revert push of the tag.
- All v2 migrations are additive: the v1.30.03 build boots and runs correctly
  against a v2-migrated database (new tables/columns are ignored). Verified by
  the harness rollback gate.
- **If v2 is rolled back while a meet is mid-adoption:** the cloud keeps the
  mirror as of the last successful upsync, but the v1 build has no sync
  endpoints, so the venue stops syncing (worker backs off harmlessly).
  Recovery: finish the day on the venue, then **USB-export the meet from the
  venue server** (Export Meet on the venue's Officials console) and import it
  on the cloud through the standard import (IDs are regenerated by that path —
  acceptable in a disaster). The cloud meet row keeps `adoption_status=
  'adopted'` which v1 ignores entirely; after returning to v2, clear it with
  Admin → Venue Adoption → Force Unlock.

## Force-unlock (R8) aftermath

- Cloud: Admin → Venue Adoption → Force Unlock (typed meet name). The venue's
  next push gets HTTP 410; its worker stops permanently and the venue home
  screen shows the red "adoption revoked" banner. Venue data stays intact.
- Recover newer-than-last-sync data from the venue via USB export → standard
  import, or from the venue's USB snapshot stick
  (`stickit_snapshot_*.db` files — plain StickIt databases).

## Venue-created logos

Meet logo files uploaded AT THE VENUE do not sync (rows only; documented
limitation, FR-12). Re-upload the logo on the cloud after check-in if one was
added at the venue.

## Athlete dedup after check-in (FR-8)

Venue-created athletes may duplicate master rows under new IDs. After check-in,
run the usual reconcile/dedup pass from the cloud Athletes admin page.

## Pi clock (FR-17)

Pi 4 has no battery clock: offline boots resume from fake-hwclock's last saved
time, so venue `datetime('now')` stamps can be stale — they are advisory only;
outbox sequence numbers order the sync, and nothing venue-side enforces
wall-clock expiry. Pi 5 (battery RTC) is preferred for future kit purchases.
